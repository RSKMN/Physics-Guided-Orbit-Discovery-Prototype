## Executive summary

The repository is a working research prototype, but it is not currently a Python
package. It has no `pyproject.toml`, `setup.py` or `setup.cfg`, no regular package
boundary, no machine-readable version and no console entry points. Its modules are
executed as scripts from the repository root or through `python -m src.<module>`.

The main findings are:

1. `src/` is an implicit namespace package, not a regular package. There is no
   `src/__init__.py`.
2. A second namespace-package fragment named `src` exists in
   `.venv/Lib/site-packages/src` and belongs to the installed REBOUND distribution
   (C headers). The project therefore shares the top-level name `src` with a
   third-party package.
3. `pip install .` cannot work because no packaging metadata exists. The project
   cannot be installed, imported from an installed location, or given console
   commands in its current form.
4. Component 2 uses `from src...` absolute imports and works as
   `python -m src.observation_generator` only when the repository root is on
   `sys.path`. Direct execution
   (`python src\observation_generator.py --help`) fails with
   `ModuleNotFoundError`.
5. Component 1 works as a direct script because it has no internal `src` imports,
   but it resolves its paths from `Path(__file__).resolve().parents[1]`. That is a
   source-checkout assumption and will break if the code is installed into
   `site-packages`.
6. Several modules execute simulations, network calls or plotting at import time
   (`src/main.py`, `src/nbody_simulator.py`, `src/nbody_realistic.py`). They are not
   safe to import and must not be placed behind a normal package import without
   first being wrapped in `main()` functions.
7. The test suite is script-based. `pytest` is not installed, and several
   `test_*.py` files execute work at module import time. Enabling pytest before
   converting them would cause collection-time simulations and data writes.
8. `requirements.txt` is unpinned and incomplete. `requirements-lock.txt` is UTF-16
   LE with a BOM, pins 14 packages, and omits `astroquery` and `pytest`. The
   installed environment is coherent (`pip check` passes), but a clean
   installation has not been verified.
9. The scientific behaviour of the current pipeline is not inherently tied to the
   working directory when running the two modern entry points from a source
   checkout, but several tests are: they pass relative data paths directly to the
   loader and fail outside the repository root.
10. The existing `docs/development/REFACTORING_PLAN.md` already proposes a target
    layout. This report confirms that direction and narrows it to a safe Phase 1
    sequence.

The recommended target is a `src`-layout package named `orbit_discovery`, with
separate Component 1 and Component 2 subpackages, a small shared `core`, thin CLI
modules, and compatibility shims for the existing `src/*.py` entry points during
migration. Existing data paths and scientific behaviour should remain untouched in
Phase 1.

### 1.5 Configuration and data contracts

The six configs are flat JSON files under `configs/`, not grouped by component.
They contain:

- `simulation_name` or `observation_name`;
- scientific initial conditions, observer model, schedule, coordinates and noise;
- output directory strings relative to the repository root;
- a plot or metadata flag.

The configs are tracked and are part of the 0.2.0 baseline. Their SHA-256 hashes
are recorded in `docs/development/BASELINE_0.2.0.md`.

Output contracts are implicit:

- `trajectory.csv` columns are documented in `docs/COMPONENT_1.md`;
- `observations.csv` contains both noisy `ra_deg`/`dec_deg` and truth columns
  `true_ra_deg`/`true_dec_deg`;
- metadata has no `schema_version` or `producer_version`;
- the observation metadata records input/config paths using the host path
  separator (backslashes on Windows);
- `run_utc` makes metadata byte-for-byte non-reproducible even when the numeric

### 2.2 Is `src/` a proper Python package?

No, not in the packaging sense.

Python 3 treats a directory without `__init__.py` as a namespace package if it is
on `sys.path`. From the repository root, `import src` succeeds as a namespace
package, and `from src.trajectory_loader import ...` works because the repository
root is the current directory and therefore on `sys.path`.

However:

- the package has no explicit identity, version or `__all__`;
- it cannot be discovered reliably by a build backend without configuration;
- the name `src` is generic and collides with a third-party directory;
- the package has no `__init__.py`, so there is no controlled place for
  `__version__`, public exports or deprecation notices.

The observed namespace path is:

```text
<module 'src' (namespace)>
  from [
    '<repo>/src',
    '<repo>/.venv/Lib/site-packages/src'
  ]
```

The second entry belongs to REBOUND 5.2.2. Its `RECORD` file includes entries such
as `src/rebound.h`, `src/simulation.h` and other C headers. The namespace package
therefore merges project code and third-party header files under the same
top-level name. This is a packaging hazard even if it currently works.

### 2.3 Can the project be installed with pip?

No. `pip install .` requires either a `pyproject.toml` with a build backend or a
legacy `setup.py`/`setup.cfg`. None exists. There is no reliable way to:

- install the project into a fresh environment;
- import it from outside the repository;
- create console scripts;
- record an installed version;
- declare supported Python versions or optional dependencies.

The current `.venv` contains only third-party packages; the project itself is not
installed. `pip list` shows no project distribution.

### 2.4 Where are `__init__.py` files needed?

They are needed at every package boundary once the project becomes a package. For
the recommended layout:

```text
src/orbit_discovery/__init__.py
src/orbit_discovery/core/__init__.py
src/orbit_discovery/component1_simulation/__init__.py
src/orbit_discovery/component2_observations/__init__.py
src/orbit_discovery/cli/__init__.py
```

They are **not** required in `src/` itself if `src/` is used only as the package
root for a `src`-layout build. In that layout, `src/` is a container, and the
importable package is `orbit_discovery`.

Adding `src/__init__.py` is not recommended as a long-term solution because it
would make `src` a regular package whose name is still generic and still collides
with the REBOUND header directory. A compatibility package named `src` can exist
temporarily during migration, but it should be treated as a shim, not the final
package.

### 2.5 Version, entry points and package data

- The version `0.2.0` exists only as a documentation label in `README.md`,
  `CHANGELOG.md` and `docs/development/BASELINE_0.2.0.md`.
- There is no `__version__`, no `importlib.metadata` lookup and no `--version`
  flag.
- There are no entry points. Users invoke scripts by path or by `python -m`.
- `configs/` is outside any package. An installed package would not contain the
  scientific configs unless they are declared as package data or passed
  explicitly.

### 3.2 Absolute versus relative imports

All project imports are absolute. There are no relative imports such as
`from .trajectory_loader import ...`.

There are two incompatible absolute-import families:

1. `from src.<module> import ...` in Component 2 and most modern tests.
2. `from horizons_loader import ...` in `src/nbody_realistic.py` and the legacy
   Horizons tests, which insert `ROOT/src` into `sys.path` first.

Moving files into a package will break both families unless shims or updates are
provided. The first family assumes the repository root is importable; the second
assumes `src/` itself is importable as a directory of top-level modules.

### 3.5 Path portability

The current path model is:

- `ROOT = Path(__file__).resolve().parents[1]` in `src/configurable_simulator.py`
  and `src/observation_generator.py`;
- `PROJECT_ROOT = Path(__file__).resolve().parent.parent` in `src/main.py` and
  `src/nbody_simulator.py`;
- `PROJECT_ROOT = Path(__file__).resolve().parents[1]` in
  `src/compare_observation_datasets.py`;
- configs store output directories relative to that root;
- observation metadata stores `input_trajectory` and `configuration_file` as
  strings produced by `Path.relative_to`, which on Windows contain backslashes.

Consequences:

- Moving or renaming the repository works as long as the internal layout is
  unchanged.
- Installing the package into `site-packages` would make
  `Path(__file__).resolve().parents[1]` point into the environment, not the
  project. Any code that depends on `ROOT` for configs or outputs would break or
  write into the wrong place.
- Running from a different CWD is safe for the two modern entry points only when
  imports are available and paths are still resolved against the source checkout.
- Metadata is not portable byte-for-byte across operating systems because of
  path separators and because of `run_utc`.
- Output directories are fixed by the configs and are overwritten on rerun. There
  is no collision-safe run ID or explicit output root.

## 5. Recommended target structure

### 5.1 Principles

The target structure should:

1. Use a real `src` layout with one importable distribution package named
   `orbit_discovery`.
2. Keep Component 1 and Component 2 in separate subpackages.
3. Put only genuinely shared code in `core`; avoid a miscellaneous `utils`
   package.
4. Keep CLI modules thin; scientific logic belongs in component modules.
5. Make configuration and data roots explicit rather than deriving them from
   `__file__`.
6. Keep existing configs, data paths and outputs unchanged during Phase 1.
7. Preserve the currently documented commands through compatibility shims until
   the migration is complete.
8. Reserve clean boundaries for Components 3 and 4 without implementing them now.
9. Make tests hermetic and pytest-compatible, with network and slow tests
   separated.
10. Keep the 0.2.0 baseline reproducible and distinguishable from future outputs.

### 5.5 Configuration and path policy

The target should replace module-global `PROJECT_ROOT` with an explicit,
documented policy:

1. CLI option `--project-root` (highest priority).
2. Environment variable `ORBIT_DISCOVERY_ROOT`.
3. Nearest ancestor containing `pyproject.toml` when running from a source
   checkout.
4. Current working directory as a last resort.

Config file paths should resolve against the project root, preserving the current
config semantics. Output paths should also resolve against an explicit output root
(`--output-root`), defaulting to the project root for backward compatibility.
The code should not create directories at import time; directory creation belongs
to the runner or CLI.

This policy keeps current behavior when a user runs from the repository root, while
allowing an installed package to work from any directory when the user supplies a
root.

### 5.6 Tests and documentation

Tests should be reorganised only after the package and path policy exist:

- `tests/unit/` for pure functions (schedule, observer, frames, noise, loader
  validation);
- `tests/integration/` for Component 1 → Component 2 runs into temporary
  directories;
- `tests/regression/` for baseline numeric comparisons;
- `tests/scientific/` for Kepler/geometry checks;
- `tests/network/` for Horizons tests, marked and skipped by default;
- `tests/fixtures/` for tiny deterministic CSVs, not full 1001-row datasets;
- `tests/legacy/` for thin wrappers around the existing scripts during migration.

Documentation should add:

- `docs/user/installation.md` with a verified clean-install procedure;
- `docs/user/quickstart.md` with the new entry points;
- `docs/components/component-1-simulation.md` and
  `component-2-observations.md`;
- `docs/schemas/` for versioned trajectory, observation, ground-truth and
  metadata contracts (Phase 2);
- `docs/development/architecture.md` for the package boundaries.

### 5.7 Versioning policy

Use one source of truth for the version. Recommended:

- `pyproject.toml` contains `version = "0.2.0"` for the first packaged release.
- `orbit_discovery.__version__` reads `importlib.metadata.version("orbit-discovery")`
  with a source-tree fallback.
- CLI commands expose `--version`.
- `CHANGELOG.md` remains the human-readable release record.

Do not duplicate the version in several modules.

### 5.8 Future Component 3 and 4 integration

The package boundaries should make future integration possible without committing
to their design now:

- Component 3 will consume the trajectory contract and a shared propagation
  service; it should not import Component 1 internals.
- Component 4 will consume observation contracts, candidate ensembles and a future
  observation window; it should not read truth.
- Evaluation will be the only layer allowed to read truth, and it should be a
  separate package boundary.
- The propagation service should be introduced in Phase 3, not invented ad hoc in
  Component 3.

These are architectural reservations only. No Component 3 or 4 code should be
written in Phase 1.

### 6.1 Preconditions

Before any file move:

1. Confirm the baseline commit and clean working tree.
2. Create an annotated tag for the baseline (recommended name:

5. Confirm that the write-producing tests are not run during packaging work.

### 6.2 Proposed sequence

| Step | Change | Why | Verification |
|---|---|---|---|
| P1.0 | Freeze the baseline: tag, hashes, clean tree | Makes every later change diffable and reversible | `git status` clean; tag exists; hashes recorded |
| P1.1 | Add `pyproject.toml` and package skeleton (`src/orbit_discovery/__init__.py`, `version.py`, empty subpackage `__init__.py` files) | Creates an installable identity without moving science code | `pip install -e .` in a disposable environment; `python -c "import orbit_discovery"` |

| P1.3 | Add shared config loaders and validation helpers as new code; leave existing loaders in place | Avoids a risky big-bang rewrite | New loader tests against existing configs |
| P1.4 | Move Component 2 pure modules (`schedule`, `observer`, `frames`, `noise`, `loader`) into the package; add compatibility shims at the old paths | Lowest-risk code move; mostly pure functions | Old and new imports produce identical arrays on fixed inputs |
| P1.5 | Move Component 2 orchestration and add `cli/observe.py`; keep `src/observation_generator.py` as a shim | Preserves documented command while adding installed entry point | `--help` from a temporary CWD; observation generation into a temp directory only, with approval |

| P1.7 | Move comparison/analysis code and add `cli/compare.py` | Completes the implemented command surface | Figure names and summary CSV columns unchanged |
| P1.8 | Add `cli/validate.py` and pytest scaffolding; keep script wrappers | Makes validation installable without breaking old commands | `pytest` default suite passes; script commands still work |
| P1.9 | Update docs, changelog and deprecation notes | Makes the new interface discoverable | README commands verified from a clean install and from outside the repo |
| P1.10 | Remove compatibility shims only after the agreed deprecation window | Avoids permanent duplicate APIs | Old paths fail with a clear migration error or are removed in a major release |

Phase 1 should stop at packaging and entry points. Scientific contract changes
(truth separation, interpolation, light-time, schema versions, propagation service)
belong to later phases in `REFACTORING_PLAN.md`.

### 6.3 Compatibility strategy

- Keep `src/configurable_simulator.py` and `src/observation_generator.py` as thin
  wrappers during migration. They should delegate to the package, not duplicate
  logic.
- Keep `src/observation_schedule.py`, `src/observer_model.py`,
  `src/coordinate_converter.py`, `src/measurement_noise.py` and
  `src/trajectory_loader.py` as re-export shims until tests and docs are updated.
- Keep the legacy top-level `horizons_loader` import working for the old test
  scripts, or update all five network scripts in one change.
- Do not move `configs/` or `data/` until the path policy and CLI are stable. If
  configs are later grouped into `configs/simulation/` and
  `configs/observations/`, keep the old flat paths for at least one release or
  provide a migration table.
- Do not change output filenames or directory layout in Phase 1. Users and
  validation scripts depend on them.

### 6.4 Validation gates for each step

Every migration step should pass:

1. **Import smoke test** from the repository root and from a temporary directory.
2. **Help test** for every implemented entry point from a temporary directory.
3. **Read-only baseline checks** that do not write into `data/`.
4. **Numeric regression** against the 0.2.0 reference outputs, using explicit
   tolerances and comparing data columns rather than metadata timestamps.
5. **Tracked-data diff check**: `git status` must show no changes under `data/`,
   `results/` or `plots/`.
6. **Import-safety check**: importing every package module must not run a
   simulation, perform network I/O, create directories or call `plt.show()`.

### 6.5 Non-goals for Phase 1

Phase 1 should not:

- change the scientific model or numerical settings;
- change interpolation, noise, observer geometry or coordinate conventions;
- separate truth from observations (Phase 2/4 work);
- add schema versions to existing artefacts (Phase 2 work);
- introduce the propagation service (Phase 3 work);
- move or rewrite the legacy Horizons workflow;
- regenerate tracked datasets;
- implement Components 3, 4 or 5;
- convert every test to pytest in one step.

## 7. Risks and safeguards

### 7.1 Risk register

| ID | Risk | Likelihood | Impact | Why it matters | Safeguard |
|---|---|---|---|---|---|
| R1 | Import breakage when `src.*` paths change | High | Medium | Component 2 and most tests import `src.*`; legacy scripts import top-level `horizons_loader` | Compatibility shims; update imports in one change; import smoke tests from root and temp CWD |
| R2 | Numeric output changes during the Component 1 move | Medium | High | Scientific results and tracked reference data would silently change | No logic changes in Phase 1; preserved call order; golden-file comparison with tolerances |
| R3 | Observation output changes during the Component 2 move | Medium | High | `observations.csv` and metadata are reference artefacts | Preserve interpolation, seed, column order and output names; compare data columns |
| R4 | Path resolution changes outputs | Medium | High | `ROOT`-relative config/output semantics are implicit | Keep current semantics in shims; introduce explicit root policy without changing defaults |
| R5 | Installed package writes into `site-packages` or wrong directories | Medium | High | `Path(__file__).parents[1]` is not a project root when installed | Replace with explicit `--project-root`/env policy before install-based use |
| R6 | Pytest collection runs simulations or network calls | High if pytest is enabled before conversion | High | `test_repeatability.py` and `test_tolerance_sensitivity.py` execute at import | Convert/guard these tests first; use markers and `testpaths`; keep network tests skipped |
| R7 | Tracked data overwritten by validation or migration tests | High | High | Configs point at tracked `data/runs` and `data/observations` | Never run writers in place; use copied configs and temp output roots; check `git status` |
| R8 | Reproducibility drift from unpinned dependencies | High | Medium | `requirements.txt` has no versions; lock is incomplete | Declare extras; regenerate a complete, UTF-8 lock in a dedicated dependency change; verify fresh install |
| R9 | `requirements-lock.txt` encoding breaks tooling | Medium | Medium | UTF-16 LE BOM makes Git and text tools treat it as binary | Convert in a dedicated step with review; do not mix with code moves |
| R10 | Package name collision with REBOUND's `src/` headers | Medium | Medium | `import src` resolves a merged namespace; fragile and confusing | Use `orbit_discovery`; do not ship a `src` package; remove shims eventually |
| R11 | Validation scripts break due to CWD-relative paths | High | Medium | Five component tests pass `"data/..."` directly | Anchor paths to an explicit project root; run tests from a temp CWD |
| R12 | Hardcoded counts/columns make tests brittle | High | Medium | 262 observations, 1001 rows, truth columns are hardcoded | Keep 0.2.0 data frozen; introduce fixtures and contract-based assertions later |
| R13 | Metadata changes from path separators or timestamps | Medium | Low/Medium | Windows backslashes and `run_utc` prevent byte-identical metadata | Compare numeric data; normalize paths; do not use metadata bytes as a regression oracle |
| R14 | Legacy network workflow becomes a base dependency | Medium | Medium | `astroquery` is not declared and requires network | Put it in an optional `network` extra; skip by default |
| R15 | Version drift between docs, package and CLI | Medium | Low | Version is currently documentation-only | Single source in `pyproject.toml`; expose `--version`; update changelog |
| R16 | Scope creep into scientific changes | Medium | High | Packaging work could accidentally alter results | Keep Phase 1 non-goals explicit; review diffs; defer contracts/science to Phases 2–4 |

### 7.2 Safeguards to adopt before the first move

1. Tag the baseline and record its commit.
2. Keep a copy of the 0.2.0 tracked data and configs outside the working tree, or
   rely on Git to restore them.
3. Record reference values for each trajectory and observation dataset:
   row counts, column names, checksums, selected numeric summaries.
4. Add a regression check that compares new outputs to the reference at shared
   epochs and columns, not by raw file bytes.
5. Never run a writer against `data/` during packaging work. Use a copied config
   with `output.directory` pointing into a temporary directory.
6. Run `git status --short` after every step and reject any change under
   `data/`, `results/` or `plots/`.
7. Keep the old entry points working until tests and docs have been updated.
8. Do not add `src/__init__.py` as a permanent solution; use `orbit_discovery`.
9. Do not enable pytest collection until the side-effecting tests are guarded or
   excluded.

### 7.3 Output-regression strategy

Because metadata contains `run_utc` and environment details, byte-for-byte
comparison of `metadata.json` is not a valid reproducibility test. Use:

- exact comparison of schema, column order and dtypes;
- exact comparison of row counts and time grids;
- tolerance-based comparison of numeric trajectory and observation columns;
- exact comparison of config-derived fields (initial conditions, bodies,
  integrator epsilon, seed, schedule, observer parameters);
- normalized path comparison in metadata;
- a separate check that `run_utc` is present but excluded from data equality.

   choice that should be reviewed.
8. **Component 3/4 CLI stubs.** This report recommends not exposing them until
   implemented. The existing `REFACTORING_PLAN.md` suggests stubs; the decision

### 1.1 Minimum Python version evidence

The minimum is determined from two independent constraints.

**Source-syntax floor: Python 3.9.**

- `src/observation_generator.py` uses `Path.is_relative_to`, introduced in
  Python 3.9, in the metadata path handling.
- No evaluated use of `match`, PEP 604 unions (`X | Y`), built-in generic
  annotations in annotations (`list[str]`, `dict[str, ...]`), `tomllib`,
  `zoneinfo`, `removeprefix`, `removesuffix`, `functools.cache` or assignment
  expressions was found in `src/*.py`.
- The `list[str]` text in `src/horizons_loader.py` is inside a docstring, not an
  evaluated annotation.

**Dependency-compatibility floor with the verified stack: Python 3.12.**

| Distribution | Verified version | `Requires-Python` |
|---|---:|---|
| NumPy | 2.5.4 | `>=3.12` |
| pandas | 3.1.0 | `>=3.11` |
| matplotlib | 3.11.2 | `>=3.11` |
| astropy | 8.0.2 | `>=3.11` |
| REBOUND | 5.2.2 | `>=3.9` |
| astroquery | 0.4.11 | `>=3.9` |

Therefore:

- **Source-only minimum:** 3.9.
- **Verified dependency minimum:** 3.12.
- **Phase 1 declared minimum:** `>=3.12`.
- **Not supported yet:** 3.9, 3.10 and 3.11, unless the project deliberately pins
  older compatible dependency versions and runs a CI matrix on those versions.

This is not an assumption based solely on the current environment. It is the
intersection of what the source uses and what the verified dependency set supports.
Lowering the floor is listed in Section 2 as an evidence gap.

## 5. Compatibility-shim strategy

### 5.1 Purpose

The shims let the documented 0.2.0 commands keep working while the implementation
moves behind the package. They are temporary and must not contain scientific logic.

### 5.2 Shim rules

1. A shim imports from the new package and delegates; it does not duplicate code.
2. Existing public names and signatures are preserved where reasonably possible.
3. Existing command forms remain valid:

   ```powershell
   python src\configurable_simulator.py configs\synthetic_asteroid.json
   python -m src.observation_generator --config configs\synthetic_observations.json
   ```

4. New command forms are added alongside, not instead of, the old ones:

   ```powershell
   orbit-simulate --config configs\synthetic_asteroid.json
   orbit-observe --config configs\synthetic_observations.json
   ```

5. No deprecation warning is emitted in Phase 1 unless it is explicitly reviewed;
   a warning on stderr could break scripts that treat stderr as failure.
6. Shims are listed in the changelog and documentation with their removal target.
7. Tests assert equivalence between the old shim path and the new package path on
   the same inputs.

### 5.3 Shim inventory

| Old path | Shim behaviour | Removed when |
|---|---|---|
| `src/configurable_simulator.py` | Import `generate_trajectory` from `component1_simulation.runner`; keep positional config and `--help`. | After the new `orbit-simulate` command is documented and one release has passed. |
| `src/observation_generator.py` | Import `generate_observations` from `component2_observations.generator`; keep `--config`. | After `orbit-observe` is documented and one release has passed. |
| `src/trajectory_loader.py` | Re-export `load_trajectory`, `REQUIRED_COLUMNS`. | When tests/docs no longer import the old path. |
| `src/observation_schedule.py` | Re-export schedule/interpolation functions. | Same. |
| `src/observer_model.py` | Re-export observer functions. | Same. |
| `src/coordinate_converter.py` | Re-export frame/RA/Dec functions. | Same. |
| `src/measurement_noise.py` | Re-export noise function and constant. | Same. |
| `src/compare_observation_datasets.py` | Delegate to `component2_observations.comparison`. | After `orbit-compare` is documented. |
| `src/horizons_loader.py` | Re-export optional network loader. | When legacy scripts are updated or archived in a later phase. |
| `src/main.py`, `src/nbody_simulator.py`, `src/nbody_realistic.py` | No shim; remain legacy scripts at current paths. | Future archive decision. |

### 5.4 What is deliberately not shimmed

- No `src/__init__.py` is added.
- No `src/orbit_discovery` alias is created for `src`.
- No estimation or selection command is shimmed or stubbed.
- No config or data path alias is created.

## 6. Dependency-group design

### 6.1 Direct imports determine the groups

| Group | Members | Evidence |
|---|---|---|
| Base | `rebound`, `numpy`, `pandas`, `matplotlib` | Direct imports in Component 1, Component 2, comparison and legacy scripts |
| Network | `astroquery` | Only `src/horizons_loader.py`; import must not happen in base package `__init__` |
| Test | `pytest` (plus plugins only when required) | Intended test runner; not installed; no current pytest imports |

`astropy` is a transitive dependency of `astroquery` and is not imported directly by
project source. It should not be listed as a direct dependency. It belongs in the
lock/network environment, not in the base group.

### 6.2 Proposed `pyproject.toml` shape

This is a design sketch, not a file created in this step.

```toml
[build-system]
requires = ["setuptools>=68", "wheel"]
build-backend = "setuptools.build_meta"

[project]
name = "orbit_discovery"
version = "0.2.0"
description = "Physics-guided orbit discovery prototype"
requires-python = ">=3.12"
dependencies = [
    "rebound>=5.2,<6",
    "numpy>=2.5,<3",
    "pandas>=3.1,<4",
    "matplotlib>=3.11,<4",
]

[project.optional-dependencies]
network = [
    "astroquery>=0.4.11,<0.5",
]
test = [
    "pytest",  # pin after the first verified test environment
]

[project.scripts]
orbit-simulate = "orbit_discovery.cli.simulate:main"
orbit-observe = "orbit_discovery.cli.observe:main"
orbit-compare = "orbit_discovery.cli.compare:main"
orbit-validate = "orbit_discovery.cli.validate:main"

[tool.setuptools]
package-dir = {"" = "src"}

[tool.setuptools.packages.find]
where = ["src"]
include = ["orbit_discovery*"]
```

Notes:

- The distribution name `orbit_discovery` is normalized by packaging tools; the
  import package remains `orbit_discovery`.
- The lower bounds above reflect the verified environment. Exact reproducible pins
  remain the job of the lock file; do not treat these ranges as a new lock.
- `pytest` remains unpinned until it is installed and verified in the test
  environment. Inventing a version here would be an unsupported claim.
- No `sim` or `analysis` extra is introduced in Phase 1. That is a proposed
  amendment to the existing plan; see Section 12.
- `matplotlib` stays in base because current modules import it at module import
  time. Moving it to an analysis extra would require a deliberate lazy-import
  change, which is out of Phase 1 scope.
- The base install must not import `astroquery`. The network extra is required only
  for the legacy Horizons path.

### 6.3 Dependency acceptance criteria

- A fresh base install can run `orbit-simulate`, `orbit-observe`, `orbit-compare`
  and `orbit-validate` with `--help`.
- The base install does not install or import `astroquery`.
- Installing the `network` extra makes `src/horizons_loader.py`-equivalent
  functionality importable.
- Installing the `test` extra allows pytest collection, subject to the guards in
  Section 10.
- `pip check` passes in the disposable environment.
- No existing scientific dependency version is changed by the packaging commit.

## 7. CLI design and command behaviour

### 7.1 Command surface

| Command | Module form | Purpose | Required inputs | Writes |
|---|---|---|---|---|
| `orbit-simulate` | `python -m orbit_discovery.cli.simulate` | Run Component 1 | `--config` (default preserves current standard config) | `trajectory.csv`, `config.json`, `metadata.json`, plots according to config |
| `orbit-observe` | `python -m orbit_discovery.cli.observe` | Run Component 2 | `--config` (default preserves current standard config) | `observations.csv`, `metadata.json` |
| `orbit-compare` | `python -m orbit_discovery.cli.compare` | Compare the three observation datasets | None in the default workflow | `comparison_summary.csv`, figures |
| `orbit-validate` | `python -m orbit_discovery.cli.validate` | Run read-only checks | None in the default workflow | None by default |

### 7.2 Common behaviour

- `--help` works from any directory and does not require a project root.
- `--version` prints the `orbit_discovery` version.
- All commands accept `--project-root PATH` and `--output-root PATH` where
  applicable. `--project-root` controls input/config resolution; `--output-root`
  controls relative output directories.
- Default scientific behaviour is unchanged:
  - same config defaults;
  - same output directory names;
  - same CSV columns and metadata meanings;
  - same seed and noise settings;
  - same plotting flags.
- CLI modules parse arguments and call a runner. They contain no REBOUND setup,
  geometry, interpolation, noise or file-format logic.
- Exit codes:
  - `0` — success;
  - `1` — controlled validation/runtime failure;
  - `2` — argument/usage error (argparse default).
- Errors go to stderr with the failing path or field. No traceback-only failures for
  expected configuration errors.

### 7.3 Command-specific behaviour

**`orbit-simulate`**

- Preserves the current positional config concept through `--config`; the old shim
  continues to accept the positional form.
- Loads the config from the project root when the path is relative.
- Preserves `move_to_com()`, IAS15 epsilon, body list, time grid and endpoint
  handling exactly.
- Writes the same output files and metadata fields.
- Does not run when `--help` is used.

**`orbit-observe`**

- Preserves `--config` and the current default.
- Resolves `input_trajectory` and `output.directory` against the project root,
  unless `--output-root` is supplied.
- Preserves linear interpolation, observer geometry, frame conversion, noise
  settings, seed, column order and metadata meanings.
- Does not separate truth columns in Phase 1.

**`orbit-compare`**

- Reads the same three dataset directories by default.
- Preserves figure filenames and `comparison_summary.csv` columns.
- Writes only under the output root; no import-time directory creation.

**`orbit-validate`**

- Runs read-only checks equivalent to the current documented validation subset.
- Does not write into `data/`, `results/` or `plots/`.
- Does not use the network by default.
- Initially covers file/data checks; in-memory scientific checks can be added only
  when explicitly migrated. No unimplemented flags are advertised.
- Returns non-zero if any executed check fails.

### 7.4 Commands deliberately not planned

- `orbit-estimate`
- `orbit-select`
- `orbit-evaluate`

Components 3–5 are not implemented. No placeholders are added in Phase 1.

## 8. Project-root and configuration-path policy

### 8.1 Root precedence

For commands that read or write project data:

| Priority | Source | Behaviour |
|---:|---|---|
| 1 | `--project-root PATH` | Use exactly this root after validating it exists. |
| 2 | `ORBIT_DISCOVERY_ROOT` | Use the environment value. Document that it should be absolute; if relative, resolve against the current directory and warn. |
| 3 | Nearest ancestor of the current directory containing `pyproject.toml` | Use the source checkout root. This preserves the current "run from repository root" workflow and also works from subdirectories. |
| 4 | No root found | Fail with an actionable error for data commands. Do not silently use the current directory. |

`--help` and `--version` do not require a root.

### 8.2 Path resolution

- A relative `--config` path resolves against the project root.
- An absolute `--config` path is used as supplied.
- Relative `input_trajectory` and `output.directory` values inside configs resolve
  against the project root, preserving 0.2.0 semantics.
- Absolute paths inside configs remain absolute.
- If `--output-root` is supplied, relative `output.directory` values resolve
  against it; absolute output paths remain absolute.
- Directory creation happens in the runner/CLI, never at module import time.
- The policy is implemented in `core/paths.py` and used by both component runners.
- No config file is rewritten to inject the root. The root is a runtime concern.

### 8.3 Installed-package behaviour

An installed `orbit-*` command run from an arbitrary directory must be given
`--project-root` or `ORBIT_DISCOVERY_ROOT` unless a source-checkout `pyproject.toml`
is found by walking up from the current directory. This avoids writing into
`site-packages` or an unrelated current directory.

### 8.4 Preserved behaviour

- Running from the repository root behaves as before.
- Running from a subdirectory of the repository now finds the root explicitly.
- Running from outside the repository requires an explicit root for data commands.
- Metadata path formatting is not intentionally changed in Phase 1. Any
  normalization is a separate contract change.

## 9. Incremental implementation sequence

Each checkpoint is a separate, reviewable change. A checkpoint may be reverted
without reverting later work. No checkpoint combines source, config, dataset and
test reorganisations.

| C4 | Component 2 generator and observe CLI | Move generator orchestration; add `cli/observe.py`; keep `src/observation_generator.py` as a shim. |
| C5 | Component 1 simulation and simulate CLI | Split config/bodies/simulator/trajectory/metadata/plotting/runner; add `cli/simulate.py`; keep `src/configurable_simulator.py` as a shim. |

## 11. Risks and rollback strategy

### 11.1 Risk register

| ID | Risk | Trigger | Mitigation | Rollback |
|---|---|---|---|---|
| MR-01 | Import breakage from moving `src.*` modules | C3–C6 | Thin shims; import smoke tests from root and temp CWD; update imports in one checkpoint. | Revert checkpoint; old paths still work. |
| MR-02 | Numeric drift in Component 1 | C5 | No logic changes; preserve call order, IAS15 settings, `move_to_com`, time grid; regression comparison. | Revert C5; restore old simulator; reference data untouched. |
| MR-03 | Observation data drift | C4 | Preserve interpolation, seed, observer defaults, frame conversion and column order; temp-root comparison. | Revert C4; old generator remains. |
| MR-04 | Config/data mutation | Any checkpoint | Configs/data are frozen; writers use temp output roots; `git status` gate. | Restore from Git; verify baseline hashes. |
| MR-05 | Test side effects during pytest collection | C8 | Guard `test_repeatability.py` and `test_tolerance_sensitivity.py`; exclude writer/network tests; add markers. | Disable pytest collection; restore data from Git. |
| MR-06 | Dependency/install drift | C1 | Do not change existing dependencies in Step 1.1; disposable environment; `pip check`; inspect wheel. | Remove `pyproject.toml`/skeleton; environment disposable. |
| MR-07 | Package-name collision | C1 | Use `orbit_discovery`; never install a `src` package; no `src/__init__.py`. | Revert package skeleton; keep source layout. |
| MR-08 | Installed command writes to wrong root | C1/C2 | Explicit root policy; no `__file__`-derived project root; error when no root. | Revert path policy; restore root-from-checkout behavior in shims. |
| MR-09 | CLI behavior differs from script | C4–C7 | CLI delegates to the same runner; old shims remain; equivalence tests. | Revert CLI checkpoint; old command remains authoritative. |
| MR-10 | Shims duplicate science | C3–C6 | Shims only import/re-export/delegate; review for duplicated code. | Revert shim; restore old module. |
| MR-11 | Config regrouping/legacy archive creep | Any checkpoint | Explicit non-goals; no config/legacy moves. | Revert; baseline paths unchanged. |
| MR-12 | Version drift | C1/C9 | Static `0.2.0`; `importlib.metadata` lookup; no bump in Phase 1. | Revert metadata change. |
| MR-13 | Windows/POSIX path differences | C2/C4 | Use `Path`; preserve current metadata formatting; test on Windows. | Revert normalization; keep current formatting. |
| MR-14 | Setuptools discovers wrong packages | C1 | Explicit `where = ["src"]` and `include = ["orbit_discovery*"]`; inspect wheel. | Fix `pyproject.toml`; no source change needed. |
| MR-15 | Lock/encoding churn | Any checkpoint | Do not edit `requirements-lock.txt` in Phase 1; separate dependency change later. | Revert dependency-file edit. |

### 11.2 Rollback procedure

1. Every checkpoint is a separate commit (in future implementation). Revert the
   checkpoint commit; do not rewrite unrelated history.
2. If tracked data changed accidentally, restore it from Git and verify the baseline
   hashes. Do not attempt to “fix” data by regenerating it.
3. If a shim breaks, restore the previous shim and keep the new package code
   unused; the old path remains functional.
4. If a numeric regression appears, stop the migration at the checkpoint, restore
   the old implementation, and compare reference and new outputs before proceeding.
5. If a packaging install fails, remove the new packaging files and use the
   disposable environment; do not uninstall or mutate the main `.venv`.
6. If a tag was created incorrectly in C0, delete the local tag before proceeding;
   do not push tags during Phase 1.
7. Keep the baseline commit and tag as the final fallback.
